## 0. 30 秒版本（背下来就能开口）

> "这是一个客户数据分析 Agent。它拿公开的 iFood 营销活动客户数据，做了三件事：
> **第一，用 RFM 和 K-Means 把客户分成能落地的人群，并且给每个人群自动生成画像标签**；
> **第二，用逻辑回归算出每个客户下次活动会响应的概率，用 Lift 验证了精准度——前 10% 的人群响应率是平均水平的 4.9 倍**；
> **第三，用一个 Agent 把'预算 2000 块投给谁、卖什么、什么渠道、什么时候发、文案怎么写、ROI 多少'这套方案自动生成出来**。
> 技术上是 FastAPI + React 的前后端分离项目，算法全部手写、不依赖 sklearn，前端 7 个页面，还有一个能用自然语言提问的对话入口。"

---

## 1. 项目要解决的问题（业务视角）

一家做食品零售/电商的企业，手里有客户的交易和行为数据，但面临三个断点：

| 断点 | 现象 | 后果 |
| --- | --- | --- |
| 看不清人 | 只有流水，没有人群画像 | 营销靠拍脑袋 |
| 算不准人 | 不知道谁会响应 | 全量群发，成本高、打扰用户 |
| 落不了地 | 分析报告给不出动作 | 报告躺在文件夹里 |

本项目把这条链路闭合：**数据 → 画像 → 预测 → 策略 → 可对话问答**。

目标用户：运营 / 市场 / 数据分析师。他们不会写 SQL，但需要「明天这批短信发给谁」。

│ 数据层                                                                                    │
│  store（单例 + 懒计算缓存） → 清洗后客户宽表 930 × 26 + 字段元数据                          │

**为什么这么分层？**

- 分析内核与外层解耦：换数据源、换前端、换模型都不影响其他部分
- `store` 单例懒计算：930 行数据所有分析在 1 秒内算完，避免每次请求重算
- Agent 只调用工具、不自己算数：保证**对话里给出的数字和页面上完全一致**（这点很多项目会翻车）

## 3. 数据从哪来（被追问最多的地方）

**答：公开数据集，不是编的。**

- 数据集名：Customer Personality Analysis（iFood 营销活动客户数据，Kaggle 公开数据集）
- 原始规模：2205 行客户 × 39 列
- 字段覆盖：客户收入、家庭结构（孩子/青少年数）、六品类消费金额、三类渠道购买次数、折扣购买次数、历史 5 次活动的接受情况、婚姻/学历 one-hot、最近一次活动是否响应（target）
- 本项目实际使用镜像 CSV + 仓库内置 1001 行样例，清洗后 **930 位客户、26 个字段**

**如果问「为什么不爬真实公司的数据」：**
1. 真实的客户交易数据涉及隐私，不能公开使用；学术与工业界做客户画像的标准做法就是用公开基准数据
2. 这个数据集的字段结构和真实零售 CRM 高度一致（RFM 三要素齐全、有活动响应标签）
3. 工程上做了数据源解耦：`scripts/prepare_data.py` 换一个下载地址/清洗逻辑即可接入企业内数据

**清洗做了什么（体现数据工程能力）：**

| 问题 | 处理 |
| --- | --- |
| 没有主键 | 生成 `customer_id`（C00001…） |
| 年龄有极端值 | 截断 18–90，并按 18–30/31–40/41–50/51–60/60+ 分箱 |
| 收入长尾 | 上截断到 99 分位 |
| 婚姻/学历是 one-hot | 反解为单列分类，便于分组统计 |
| 六个品类的金额是 Mnt* 命名 | 统一映射为业务语义字段 + 中文标签（字段字典落库到 `dataset_meta.json`） |
| 无缺失值/无重复 | 干净数据，脚本里仍然做了校验并记录到元数据（`missing_cells=0, duplicate_rows=0`） |

> 数字兜底：`GET /api/dataset` 会返回行列数、字段字典、缺失与重复数，页面上「数据说明」页也能看到。**被问到数据细节时，直接打开这页。**

## 4. 三个核心算法（讲原理 + 讲为什么 + 讲结果）

### 4.1 RFM 分层——先解决"谁值钱"

- **R（Recency）**：最近一次购买距今多少天，越小越好
- **F（Frequency）**：购买频次
- **M（Monetary）**：累计消费金额
- 打分方式：**五分位**（把客户按每个指标排序，切 5 等份，分别给 1–5 分），R/F/M 都 ≥3 记为「高」，组合出 8 类客群

为什么用五分位而不是固定阈值：不同行业金额量级完全不同，分位打分**天生可迁移**，换一家公司不用重新调阈值。

当前结果（930 人）：

| 分层 | 人数 | 占比 | 营收占比 |
| --- | --- | --- | --- |
| 重要价值客户 | 334 | 35.9% | **58.5%** |
| 重要保持客户 | 219 | 23.6% | 37.3% |
| 一般发展客户 | 221 | 23.8% | 2.2% |
| 一般挽留客户 | 146 | 15.7% | 1.6% |

**能讲的洞察**：超过一半营收来自 35.9% 的重要价值客户，是典型「二八结构」；同时 23.6% 的重要保持客户（买得多但很久没来）是**最容易用一次召回活动救回来**的群体。

> 为什么有些分层只有 1–4 人？因为 R/F/M 在这份数据里**强正相关**（最近买过的人通常也买得频繁、金额高），「R 高但 F、M 低」这类交叉组合天然稀少。这不是 bug，而是一个可以讲的发现：**客户价值是分化而非均匀分布的**。

### 4.2 K-Means 聚类——再解决"像什么人"

- 特征：收入、总消费、购买频次、最近间隔、折扣购买数、月访问次数、年龄（标准化）
- 手写实现：**k-means++ 初始化 + 10 次重启取最优最小 SSE**，用**轮廓系数**选 k（对比 k=2..6）
- 结果：k=4，轮廓系数 0.2232

| 客群 | 人数 | 占比 | 营收占比 | 标签 |
| --- | --- | --- | --- | --- |
| 核心高价值客群 | 305 | 32.8% | **69.1%** | 高收入 / 高价值 / 高频复购 / 葡萄酒重度用户 / 活动敏感型 |
| 稳定贡献客群 | 182 | 19.6% | 23.1% | 高频复购 / 银发群体 / 葡萄酒重度用户 |
| 潜力成长客群 | 236 | 25.4% | 4.1% | 价格敏感 / 低客单 / 近期活跃 / 有孩家庭 |
| 长尾基础客群 | 207 | 22.3% | 3.7% | 价格敏感 / 低客单 / 濒临流失 |

**客群怎么自动命名？** 按 `0.5×z(消费) + 0.3×z(频次) − 0.2×z(间隔)` 排一个综合分，分数从高到低依次命名（核心高价值 → 稳定贡献 → 潜力成长 → 长尾基础），并给出「活跃 / 沉默预警」状态。这样换数据也不会出现名字对不上的问题。

**标签怎么来？** 规则生成，可解释：收入高于全量 75 分位 → 高收入；折扣购买占比高 → 价格敏感；间隔 > 90 天 → 濒临流失；品类占比最高 → 「葡萄酒重度用户」……**标签不是模型吐出来的黑盒，而是把统计口径写成规则**，这是能讲清楚的关键。

### 4.3 逻辑回归响应预测——最后解决"谁会买"

**为什么用逻辑回归而不是 XGBoost？**
1. 正样本只有 13.5%，树模型容易过拟合，逻辑回归 + 类别加权更稳
2. **可解释性**：每个特征有一个系数，能直接告诉运营「历史活动接受数每 +1，响应胜算提高多少」——这正是业务方最想要的
3. 手写实现约 150 行，能逐行讲清梯度下降

**训练细节（会被追问，记住这几点）：**

- 13 个特征，标准化后训练
- 类别不平衡：正样本权重 `w+ = n/(2·n+)`，负样本 `w- = n/(2·n-)`
- L2 正则，批量梯度下降，`random_state=42`，70/30 分层划分
- **阈值不是拍的**：在验证集上 0.05–0.80 网格搜索，最大化 F1 得到 **0.58**

**当前结果：**

| 指标 | 值 | 怎么讲 |
| --- | --- | --- |
| AUC | 0.887 | 排序能力好：随机抽一个响应客户和一个不响应客户，模型有 88.7% 概率把响应客户排前面 |
| 精确率 | 0.483 | 被判为"会响应"的人里约一半真的响应（基线只有 13.5%） |
| 召回率 | 0.800 | 真正会响应的客户，抓到了 80% |
| F1 | 0.602 | 精确率与召回率的调和平均 |

**Lift 表（业务最值钱的一张表）：**

| 分位 | 人数 | 平均预测分 | 实际响应率 | Lift |
| --- | --- | --- | --- | --- |
| 第 1 组（Top 10%） | 93 | 0.91 | **66.7%** | **4.92** |
| 第 2 组 | 93 | 0.67 | 28.0% | 2.06 |

**这句话必须会说**："愿意触达前 10% 的人群，响应率是随机投放的 4.9 倍——也就是成本不变的情况下，转化提升近 5 倍。"

**特征系数（谁在推高响应）：**

| 特征 | 系数 | 解读 |
| --- | --- | --- |
| 历史活动接受数 | +0.96 | 参加过活动的人更容易再参加（最佳预测因子） |
| 家中青少年数 | −0.78 | 有青少年的家庭响应更保守 |
| 最近购买间隔 | −0.72 | 越久没买越难唤醒 |
| 折扣购买次数 | +0.63 | 折扣敏感人群对活动更买账 |

### 4.4 Apriori 关联规则——解决"搭配卖什么"

- 每位客户买过的品类作为一个「购物篮」，挖掘 1~2 元频繁项集
- 三个指标：支持度（多少人同时买）、置信度（买了 A 的人里多少买 B）、**提升度**（比随机买 B 高多少倍）

最强规则：**水果 → 甜食**，支持度 72.5%、置信度 89.3%、提升度 1.09。

**要主动说清局限**：提升度只有 1.09，说明「买了水果的人买甜食」只比普通人高 9%——因为这份数据里各品类消费金额高度相关，几乎所有客户都买多个品类。**能讲出"这个规则弱、不适合做主打推荐，更适合做凑单"比硬吹更有说服力。**

## 5. 营销方案怎么生成（把分析变成动作）

输入：目标客群 + 预算 + 单客成本 + 折扣力度。
输出六件事，全部有数据依据：

| 决策 | 依据 | 示例（核心高价值客群，预算 2000 元） |
| --- | --- | --- |
| 发给谁 | 按响应概率排序取 Top N，`N = 预算 ÷ 单客成本` | 250 人，覆盖该客群 82% |
| 卖什么 | 该客群消费最高的品类 Top3 + 关联规则加购 | 葡萄酒（人均 603）> 肉类（389）> 鱼类（84） |
| 走哪个渠道 | 该客群三类渠道购买次数占比最大者 | 线下门店 |
| 什么时候发 | 按平均最近购买间隔分 3 档 | 本周三 19:00–21:00 |
| 优惠怎么给 | 按客群价格敏感度 + 折扣力度 | 组合套装立减 10% |
| 值不值 | `预计营收 = 人数 × 响应率 × 客单价`，`ROI = 营收 ÷ 成本` | ROI ≈ 2.4–3.3，优先级 P0 |

好方案的标准是**每个数字都能倒推**：为什么是 250 人（预算 2000 ÷ 8）、为什么是葡萄酒（该客群品类消费占比 47.7%）、为什么是周三晚上（客群平均 3 天内有过购买）。

## 8. 高频追问（提前准备）

**Q1：这个项目最大的创新点是什么？**
A：不是算法新，而是**把"分析—决策—对话"闭合了**。多数课程项目停在"跑出几个图"，这个项目多做了两件事：一是把模型输出直接翻译成可执行的营销方案（圈人/选品/渠道/时机/ROI），二是用 Agent 把 7 个分析工具串起来，让不会 SQL 的人也能问数据。

**Q2：为什么不直接用现成的 BI 工具（Tableau/PowerBI）？**
A：BI 能看数不能决策也听不懂人话。这里的价值在**模型层**（响应概率、聚类命名）和**Agent 层**（自然语言→工具调用→渲染），这两块 BI 做不了。

**Q3：930 行数据能说明什么？**
A：说明方法论与工程链路。真实生产需要更大样本、时间窗滚动验证和 A/B 实验；这点项目文档里是明确写出来的，不回避。

**Q4：轮廓系数只有 0.22，聚类是不是很差？**
A：食品零售的品类消费高度相关，客户在特征空间里是连续分布而非天然成团。0.22 属于「有结构但不强」，所以聚类结果只作为**人群切分参考**，最终决策用的是 RFM + 响应概率这两个更稳的口径。

**Q5：精确率 0.48 是不是太低了？**
A：基线响应率只有 13.5%，精确率 0.48 相当于**提升 3.6 倍**；而且业务上未响应的成本很低（一条短信），所以更看重召回率（0.80）和 Lift（4.9）。阈值 0.58 是 F1 最优，如果更在意成本可以调高阈值换精确率。

**Q6：如果数据量到 1000 万行怎么办？**
A：现在全内存计算，需要改造三处：① 清洗落 Parquet + 分批读取；② 模型训练离线预计算、结果入库（Redis/Postgres），API 只查结果；③ 聚类与关联规则换 Spark/ClickHouse。接口契约不用变。

**Q7：Agent 会不会瞎编数字？**
A：不会。Agent 只做「选工具 + 传参数」，所有数字由工具从同一份数据算出来；在线模式下也只允许调用已注册的 7 个工具。没有 Key 时退化为规则引擎，行为完全一致。

**Q8：怎么验证模型有效而不是过拟合？**
A：70/30 分层划分，阈值在验证集搜索、指标在测试集报告；全量指标（AUC 0.87）与测试集（0.887）接近，说明没有明显过拟合。真正的验证要靠 A/B 实验，这是下一步。

**Q9：为什么阈值不用 0.5？**
A：正样本只有 13.5%，0.5 会过度保守导致召回塌陷。用验证集 F1 网格搜索得到 0.58，兼顾精确率与召回率。这个细节最能体现对不平衡分类的理解。

**Q10：这个项目能落地到真实企业吗？**
A：可以直接替换数据源跑通，需要的改造是：① 对接 CRM 数据仓库；② 接真实触达通道（短信/企微/邮件 SDK）；③ 加权限与审计；④ 建立 ROI 回流闭环做持续优化。

**Q11：前端为什么用 ECharts 不用别的？**
A：图表类型全（热力图、矩形树图、双轴、雷达），中文生态好，按需引入后体积可控。

**Q12：项目里有没有用到大模型？**
A：有，但是**可选的**：配了 `LLM_BASE_URL/LLM_API_KEY` 就走 Function Calling，不配就走规则引擎。这样既展示了大模型应用能力，又保证离线可演示——这是工程上很实用的取舍。

**Q13：为什么写这么多个后端模块，不能一个文件？**
A：一个文件写到 1500 行无法维护也无法测试。这里按「指标/分层/聚类/画像/预测/关联/方案」单一职责拆分，每个模块都能单独跑、单独验证，`store` 负责组装与缓存。

## 9. 主动承认的不足（比藏着更有说服力）

1. 数据规模小、单时点快照，没有时间序列趋势与因果推断
2. 关联规则提升度接近 1，实际推荐价值有限
3. 响应模型是线性模型，特征交互靠人工构造
4. 没有 A/B 实验与 ROI 回流闭环，ROI 是估算不是实测
5. 前端未做权限与多租户，生产部署还需要 Nginx + 鉴权

## 10. 下一步计划（被问"还能做什么"时用）

1. 接入真实触达通道 + A/B 实验框架，把 ROI 从估算变成实测
2. 用 GBDT + 特征交叉对比线性模型，目标 AUC 提升到 0.92+
3. 加入时间序列的客户生命周期预测（CLV）
4. 把分析结果物化到数据库，支持千万级数据与多租户
5. Agent 增加「多轮追问 + 报告一键导出」
