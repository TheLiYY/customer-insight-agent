## 0. 30 秒版本（背下来就能开口）

> "这是一个客户数据分析 Agent。它拿 Kaggle 上公开的 iFood 营销活动客户数据（2205 行 × 39 列），做了四件事：
> **第一，用 RFM 和 K-Means 把客户分成能落地的人群，并给每个人群自动生成画像标签**；
> **第二，用逻辑回归算出每个客户下次活动的响应概率，用 Lift 验证了精准度——前 10% 的人群响应率是平均水平的 4.5 倍**；
> **第三，跑完分析自动生成 10 条结论**，每条都带数据证据和下一步动作，不用人再写报告；
> **第四，用一个 Agent 把'预算 2000 块投给谁、卖什么、什么渠道、什么时候发、文案怎么写、ROI 多少'这套方案自动生成出来**。
> 技术上是 FastAPI + React 的**前后端分离**项目，算法用 scikit-learn 和 mlxtend，前端 9 个页面，还有一个能用自然语言提问的对话入口。"

## 1. 项目要解决的问题（业务视角）

一家做食品零售/电商的企业，手里有客户的交易和行为数据，但面临四个断点：

| 断点 | 现象 | 后果 |
| --- | --- | --- |
| 看不清人 | 只有流水，没有人群画像 | 营销靠拍脑袋 |
| 算不准人 | 不知道谁会响应 | 全量群发，成本高、打扰用户 |
| 读不懂数 | 图表一堆，没人下结论 | 报告躺在文件夹里 |
| 落不了地 | 分析结果给不出动作 | 分析师和运营各说各话 |

本项目把这条链路闭合：**数据 → 画像 → 预测 → 结论 → 策略 → 可对话问答**。

目标用户：运营 / 市场 / 数据分析师。他们不会写 SQL，但需要「明天这批短信发给谁」。

```
┌──────────────────────────────────▼────────────────────────────────────────────────┐
│ FastAPI 服务层（纯 API，不托管前端）                                                 │
│  api/routes.py（14 个分析接口）   agent/routes.py（对话）   /docs /redoc 自动文档     │
├───────────────────────────────────────────────────────────────────────────────────┤
│ Agent 编排层                                                                        │
│  orchestrator：意图识别 → 选工具 → 传参数 → 组装渲染块                                │
│  ├─ 在线：LLM Function Calling（OpenAI 兼容协议）                                     │
│  └─ 离线：关键词 + 正则规则引擎（无 Key 兜底）                                        │
│  tools：8 个分析工具，输出 text / kpi / chart / table 四种渲染块                      │
├───────────────────────────────────────────────────────────────────────────────────┤
│ 分析内核（scikit-learn + mlxtend，核心层不依赖 FastAPI，可脱离 Web 复用）            │
│  rfm │ clustering │ persona │ propensity │ association │ insights │ campaign │ overview│
├───────────────────────────────────────────────────────────────────────────────────┤
│ 数据层                                                                              │
│  store（单例 + 懒计算缓存）→ 清洗后宽表 2021 × 25 + 字段元数据                        │
│  原始数据：Kaggle Customer Personality Analysis（2205 × 39 特征工程版）              │
└───────────────────────────────────────────────────────────────────────────────────┘
```

**为什么这么分层？**

- 分析内核与外层解耦：换数据源、换前端、换模型都不影响其他部分（`core/` 里连 FastAPI 都不 import）
- `store` 单例懒计算：2021 行数据首次全算约 2 秒，之后毫秒级，避免每次请求重算
- Agent 只调用工具、不自己算数：保证**对话里给出的数字和页面上完全一致**（这点很多项目会翻车）
- 前后端分离：前端可独立部署/回滚，后端只提供 JSON，便于以后接 App、小程序

**怎么跑起来（三种场景，一句话一个）**

| 场景 | 命令 | 说明 |
| --- | --- | --- |
| 本机开发 | `python backend/run.py` + 本地 Nginx（`deploy/nginx.conf`） | 改前端源码后 `pnpm build` 立刻生效 |
| 一台机器完整跑 | `docker compose up -d --build` → http://localhost:8080 | web（Nginx）+ api（FastAPI）两个容器，只有一个对外端口 |
| 换机器交付 | `deploy/make-bundle.ps1` 打包 → 目标机 `docker load -i images.tar` + `docker compose up -d` | 目标机只要 Docker，不用 Python/Node，不用联网 |

> 只有 Nginx 一前端方式：本地用 `deploy/nginx.conf`，容器里用 `deploy/nginx.docker.conf`，两者规则一致（静态 + `/api` 反代 + SPA 回落）。

## 3. 数据从哪来（被追问最多的地方）

**答：公开数据集，不是编的。**

- 数据集名：Customer Personality Analysis（iFood 营销活动客户数据，Kaggle 公开数据集）
- 来源页：<https://www.kaggle.com/datasets/imakash3011/customer-personality-analysis>
- 实际使用镜像（已做特征工程的宽表）：`https://cdn.jsdelivr.net/gh/nailson/ifood-data-business-analyst-test@master/ifood_df.csv`
- 原始规模：**2205 行客户 × 39 列**
- 字段覆盖：客户收入、家庭结构（孩子/青少年数）、六品类消费金额、三类渠道购买次数、折扣购买次数、历史 5 次活动的接受情况、婚姻/学历 one-hot、最近一次活动是否响应（target）
- 清洗后用于建模：**2021 位客户、25 个字段**（原始 2205 行 → 去重 184 行 → 2021 行有效客户）

**如果问「为什么不爬真实公司的数据」：**
1. 真实的客户交易数据涉及隐私，不能公开使用；学术与工业界做客户画像的标准做法就是用公开基准数据
2. 这个数据集的字段结构和真实零售 CRM 高度一致（RFM 三要素齐全、有活动响应标签）
3. **工程上已经解耦了数据源**：任何客户表丢进去都能跑，见下面「换数据」那段——这是最能体现工程能力的一问

**清洗做了什么（体现数据工程能力）：**

| 问题 | 处理 |
| --- | --- |
| 没有主键 | 生成 `customer_id`（C00001…） |
| 年龄有极端值 | 截断 18–90，并按 18–30/31–40/41–50/51–60/60+ 分箱 |
| 收入长尾 | 上截断到 99 分位 |
| 婚姻/学历是 one-hot | 反解为单列分类，并映射成中文（本科/硕士/博士…） |
| 六个品类的金额是 `Mnt*` 命名 | 统一映射为业务语义字段 + 中文标签（字段字典落 `dataset_meta.json`） |
| 有重复行 | 去掉 184 条完全重复的记录，剩余 2021 行；关键字段（收入/金额）缺失的客户剔除，其余按 0 补齐 |

> 数字兜底：`GET /api/dataset` 会返回行列数、字段字典、缺失与重复数，页面上的「数据说明」页也能看到。**被问到数据细节时，直接打开这页。**

**关于"用 Excel 数据训练"**：项目里的数据全部是 Excel 可打开的 CSV/xlsx。
`Customer_Personality_Analysis.xlsx` 是**数据源表**（2205 行原始明细 + 字段字典），
`Customer_Insight_Report.xlsx` 是**结果报告**（9 个 sheet + 4 张原生图表）。
模型训练与测试读的是 `customers.csv`（由原始数据清洗而来），两个 Excel 是给业务方核对和交付用的。

**换成自己的 Excel 数据训练**：一条命令，列名不用改。

```bash
python scripts/prepare_data.py --file 客户数据.xlsx            # 也可以 --sheet 指定工作表
python scripts/prepare_data.py --dataset mall                 # 内置第二套：商场会员（只有年龄/性别/收入/消费评分）
python scripts/prepare_data.py --dataset bank                 # 内置第三套：银行营销（有 y 响应标签、没有金额）
```

**这背后是「数据契约层」（`backend/app/core/schema.py`），讲的时候可以这么说：**

1. 原来 `prepare_data.py` 里写死了 39 个 iFood 列名，换一份数据就报错——这是耦合。
2. 现在多了一层：把任意列名**规范化**（去空格下划线、转小写、保留中文）→ 拿每个列名去撞**别名表**（3 完全一致/2 前缀/1 包含）→ 再校验**内容**像不像（数值列可转换率 ≥80%、二值列接受 `y/yes/no/是/否`、品类列均值 ≥1）。
3. 认出来的写成 `mapping.json`（哪个标准字段来自哪列 + 置信度 + 没被用上的列），排查有据可查。
4. 认不出来的字段就**标记缺失**，输出一份 `capabilities`（有没有收入/金额/间隔/频次/响应标签），后端和前端据此**降级**：没有金额就不算 ROI，没有响应标签就不做响应预测、页面换成说明卡——**不是崩，是退化**。

三套数据的实测结果（冒烟测试都是 21/21 通过）：

| 数据集 | 有效客户 | 能算什么 | 演示时能说明什么 |
| --- | --- | --- | --- |
| iFood（默认） | 2021 | 全部能力 | 完整链路 |
| Mall Customers | 200 | 画像、聚类（无金额/无日期/无响应） | 缺字段时如何优雅降级 |
| Bank Marketing | 4119 | 画像、聚类、响应预测（无金额） | 有标签没金额也能练模型 |

## 4. 三个核心算法（讲原理 + 讲为什么 + 讲结果）

### 4.1 RFM 分层——先解决"谁值钱"

- **R（Recency）**：最近一次购买距今多少天，越小越好
- **F（Frequency）**：购买频次
- **M（Monetary）**：累计消费金额
- 打分方式：**五分位**（按每个指标排序切 5 等份给 1–5 分，R 方向反转），R/F/M 都 ≥3 记为「高」，组合出 8 类客群

为什么用五分位而不是固定阈值：不同行业金额量级完全不同，分位打分**天生可迁移**，换一家公司不用重新调阈值。

当前结果（2021 人）：

| 分层 | 人数 | 占比 | 营收占比 | 响应率 |
| --- | --- | --- | --- | --- |
| 重要价值客户 | 715 | 35.4% | **56.3%** | 24.4% |
| 重要保持客户 | 488 | 24.2% | 39.6% | 12.3% |
| 一般发展客户 | 493 | 24.1% | 2.4% | 14.4% |
| 一般挽留客户 | 307 | 15.4% | 1.6% | 3.5% |
| 其余 4 层 | 18 | 1.0% | 0.2% | — |

**能讲的洞察**：56.3% 的营收来自 35.4% 的重要价值客户，典型「二八结构」；另有 24.2% 的重要保持客户（买得多但很久没来）是**最容易用一次召回活动救回来**的群体，而且他们的响应率只有 12.3%，说明过去被忽略。

> 为什么有些分层只有 1–8 人？因为 R/F/M 在这份数据里**强正相关**（最近买过的人通常也买得频繁、金额高），「R 高但 F、M 低」这类交叉组合天然稀少。这不是 bug，而是一个可以讲的发现：**客户价值是分化而非均匀分布的**。

### 4.2 K-Means 聚类——再解决"像什么人"

- 特征：收入、总消费、购买频次、最近间隔、折扣购买数、月访问次数、年龄（标准化）
- 实现：`StandardScaler` + `KMeans(n_init=10, random_state=42)`，用 `silhouette_score` 评估 k=2..6（抽样 1500 加速）
- 结果：**k=4，轮廓系数 0.2163**，簇中心用 `scaler.inverse_transform` 还原成真实量纲

| 客群 | 人数 | 占比 | 营收占比 | 状态 | 标签 |
| --- | --- | --- | --- | --- | --- |
| 核心高价值客群 | 687 | 34.0% | **71.5%** | 活跃 | 高收入 / 高价值 / 高频复购 / 葡萄酒重度用户 / 活动敏感型 |
| 稳定贡献客群 | 361 | 18.1% | 20.6% | 活跃 | 高频复购 / 银发群体 / 葡萄酒重度用户 / 折扣依赖 |
| 潜力成长客群 | 508 | 25.0% | 4.3% | 活跃 | 价格敏感 / 低客单 / 近期活跃 / 有孩家庭 |
| 长尾基础客群 | 465 | 23.3% | 4.3% | **沉默预警** | 价格敏感 / 低客单 / 濒临流失 / 有孩家庭 |

**客群怎么自动命名？** 按 `0.5×z(消费) + 0.3×z(频次) − 0.2×z(间隔)` 排一个综合分，从高到低依次命名（核心高价值 → 稳定贡献 → 潜力成长 → 长尾基础），并给出「活跃 / 沉默预警」状态。换数据也不会出现名字对不上的问题。

**标签怎么来？** 规则生成，可解释：收入高于全量 75 分位 → 高收入；折扣购买占比高 → 价格敏感；间隔 > 90 天 → 濒临流失；品类占比最高 → 「葡萄酒重度用户」……**标签不是模型吐出来的黑盒，而是把统计口径写成规则**，这是能讲清楚的关键。

### 4.3 逻辑回归响应预测——最后解决"谁会买"

**为什么用逻辑回归而不是 XGBoost？**
1. 正样本只有 15.5%，树模型容易过拟合，逻辑回归 + `class_weight="balanced"` 更稳
2. **可解释性**：每个特征有一个系数，能直接告诉运营「历史活动接受数每增加，响应胜算提高多少」——这正是业务方最想要的
3. 用 sklearn 的 `LogisticRegression` + `Pipeline`，标准化与模型绑定，杜绝"训练标准化了、预测忘了"的经典 bug

**训练细节（会被追问，记住这几点）：**

- 13 个特征，`Pipeline(StandardScaler → LogisticRegression)`，C=1.0，max_iter=2000
- 类别不平衡：`class_weight="balanced"`（等价于按类频率反比加权）
- 70/30 **分层**切分（`stratify=y`），保证两边正样本比例一致
- **阈值不是拍的**：用 `precision_recall_curve` 直接拿到所有阈值下的 P/R，取 F1 最大处 → **0.59**
- 评估完再用全量数据重训一次出分，这样名单里每个人的概率都用了全部信息

**当前结果（测试集 30%）：**

| 指标 | 值 | 怎么讲 |
| --- | --- | --- |
| AUC | **0.8827** | 排序能力好：随机抽一个响应客户和一个不响应客户，模型有 85.7% 概率把响应客户排前面（全量重训后 0.8884） |
| 准确率 | 0.8913 | 整体判对率 |
| 精确率 | 0.690 | 被判为"会响应"的人里约一半真的响应（基线只有 15.5%，提升 3.3 倍） |
| 召回率 | 0.527 | 真正会响应的客户，抓到了 70% |
| F1 | 0.5976 | 精确率与召回率的调和平均 |

**Lift 表（业务最值钱的一张表）：**

| 分位 | 人数 | 平均预测分 | 实际响应率 | Lift | 覆盖响应客户 |
| --- | --- | --- | --- | --- | --- |
| 第 1 组（Top 10%） | 203 | 0.931 | **69.5%** | **4.51** | 45.3% |
| 第 2 组 | 203 | 0.7324 | 33.0% | 2.14 | 21.5% |

**这句话必须会说**："只触达前 10% 的人群，响应率是随机投放的 4.5 倍——成本不变，转化提升 4 倍多。"

**特征系数（谁在推高响应）：**

| 特征 | 系数 | 解读 |
| --- | --- | --- |
| 历史活动接受数 | +0.836 | 参加过活动的人更容易再参加（最佳预测因子） |
| 门店购买次数 | −0.778 | 门店型客户对新活动更保守（更依赖现场体验） |
| 最近购买间隔 | −0.767 | 越久没买越难唤醒 |
| 家中青少年数 | −0.677 | 有青少年的家庭响应更保守 |
| 月访问次数 | +0.687 | 线上活跃度高的人更容易被打动 |

### 4.4 Apriori 关联规则——解决"搭配卖什么"

- 用 `TransactionEncoder` 把每个客户的品类购买转成 0/1 矩阵，`apriori(min_support=0.03, max_len=2)`
- 三个指标：支持度（多少人同时买）、置信度（买了 A 的人里多少买 B）、**提升度**（比随机买 B 高多少倍）

最强规则：**甜食 → 鱼类**，支持度 73.3%、置信度 90.0%、提升度 1.09。

**要主动说清局限**：提升度只有 1.09，说明「买了甜食的人买鱼类」只比普通人高 9%——因为这份数据里各品类渗透率都在 90% 以上，几乎所有客户都买多个品类。**能讲出"这个规则弱、不适合做主打推荐，更适合做凑单/组合套餐"比硬吹更有说服力**，而且项目的自动结论里就是这么写的。

### 4.5 自动结论引擎——解决"所以呢？"

这是这次新增的能力：**分析跑完，系统自己下结论**，不用人再对着图表写报告。

- 输入：本次所有分析结果（KPI、RFM、客群画像、模型指标、关联规则、品类渗透率）
- 规则：9 类判断逻辑（价值集中度、沉默风险、投放效率、商品结构、关联强度、渠道结构、人群结构、折扣依赖、投诉率）
- 输出：每条结论是 `标题 + 结论 + 证据链 + 建议动作`，并标 `opportunity / risk / insight`
- 当前产出 **10 条**：2 条增长机会、4 条风险预警、4 条结构洞察

示例（首页那句话就是自动生成的）：

> "2021 位客户里，前 20% 贡献了 53.6% 的营收；按响应概率筛选后的头部名单，转化率是平均水平的 4.51 倍。"

**为什么重要**：很多人做数据分析项目，图表画得很好，但一被问「所以呢」就卡住。这个模块把"结论"变成了产品的一部分，而且是**可追溯的确定性规则**——每条都能报出具体数字，不会像大模型那样编。

## 5. 营销方案怎么生成（把分析变成动作）

输入：目标客群 + 预算 + 单客成本 + 折扣力度。
输出六件事，全部有数据依据：

| 决策 | 依据 | 示例（核心高价值客群，预算 2000 元，单客 8 元） |
| --- | --- | --- |
| 发给谁 | 按响应概率排序取 Top N，`N = 预算 ÷ 单客成本` | 250 人，覆盖该客群 36.4% |
| 卖什么 | 该客群消费最高的品类 Top3 + 关联规则加购 | 葡萄酒（人均 603，占 47.9%）> 肉类（383，30.5%）> 鱼类（83，6.6%） |
| 走哪个渠道 | 该客群三类渠道购买次数占比最大者 | 线下门店（44.2%） |
| 什么时候发 | 按平均最近购买间隔分 3 档 | 本周三 19:00–21:00 |
| 优惠怎么给 | 按客群价格敏感度 + 折扣力度 | 组合套装立减 10% |
| 值不值 | `预计营收 = 人数 × 平均响应概率 × 客单价`，`ROI = 营收 ÷ 成本` | 预计响应 209 人、营收 16,388 元、**ROI 7.19**、优先级 P0 |

好方案的标准是**每个数字都能倒推**：为什么是 250 人（预算 2000 ÷ 8）、为什么是葡萄酒（该客群品类消费占比 47.9%）、为什么是周三晚上（客群平均最近购买间隔在近期档）。

> 主动说明：ROI 7.19 是"理想口径"，只算了触达成本，没算物流、退货、毛利。真实业务里会低不少，这一点写在文档和自动结论里。

## 8. 高频追问（提前准备）

### Q0：如果公司给的数据和 Kaggle 完全不一样，还能跑吗？
能，见第 3 节「换数据」那段。一句话版本：**列名自动识别 + 缺失能力自动降级**，
三套差异极大的数据（iFood / 商场会员 / 银行营销）都在同一套代码上跑通了，
换数据只要 `python scripts/prepare_data.py --file 你的表.xlsx`。

### 其余高频问题

**Q1：这个项目最大的创新点是什么？**
A：不是算法新，而是**把"分析—结论—决策—对话"闭合了**。多数课程项目停在"跑出几个图"，这个项目多做了三件事：一是跑完自动出 10 条可追溯的结论；二是把模型输出翻译成可执行的营销方案（圈人/选品/渠道/时机/ROI）；三是用 Agent 把 8 个分析工具串起来，让不会 SQL 的人也能问数据。

**Q2：为什么不直接用现成的 BI 工具（Tableau/PowerBI）？**
A：BI 能看数不能决策也听不懂人话。这里的价值在**模型层**（响应概率、聚类命名）、**结论层**（自动生成判断）和**Agent 层**（自然语言→工具调用→渲染），这三块 BI 做不了。

**Q3：2021 行数据能说明什么？**
A：说明方法论与工程链路。真实生产需要更大样本、时间窗滚动验证和 A/B 实验；这点项目文档里是明确写出来的，不回避。

**Q4：轮廓系数只有 0.2163，聚类是不是很差？**
A：食品零售的品类消费高度相关，客户在特征空间里是连续分布而非天然成团。0.2 左右属于「有结构但不强」，所以聚类结果只作为**人群切分参考**，最终决策用的是 RFM + 响应概率这两个更稳的口径。

**Q5：精确率 0.51 是不是太低了？**
A：基线响应率只有 15.5%，精确率 0.51 相当于**提升 3.3 倍**；而且业务上未响应的成本很低（一条短信），所以更看重召回率（0.70）和 Lift（4.51）。阈值 0.78 是 F1 最优；如果更在意触达成本，可以调高阈值换精确率。

**Q6：为什么用 scikit-learn，不手写算法？**
A：手写能体现原理理解，但生产项目应该用经过验证的实现：`StandardScaler` 防数据泄漏、`precision_recall_curve` 比手写循环更准更快、`class_weight` 是处理不平衡的标准做法、`mlxtend` 的 Apriori 有完整文档与测试。**算法原理我写在 `docs/GLOSSARY.md` 里逐条讲透，代码交给库——两者不冲突，反而是工程素养的体现。**

**Q7：如果数据量到 1000 万行怎么办？**
A：现在全内存计算，需要改造三处：① 清洗落 Parquet + 分批读取；② 模型训练离线预计算、结果入库（Redis/Postgres），API 只查结果；③ 聚类与关联规则换 Spark/ClickHouse。**接口契约不用变**，这也是前后端分离 + store 抽象带来的好处。

**Q8：Agent 会不会瞎编数字？**
A：不会。Agent 只做「选工具 + 传参数」，所有数字由工具从同一份数据算出来；在线模式也只允许调用已注册的 8 个工具，系统提示里明确要求"先调工具再回答"。没有 Key 时退化为规则引擎，行为完全一致。

**Q9：怎么验证模型有效而不是过拟合？**
A：70/30 分层划分，阈值在验证集搜索、指标在测试集报告；全量重训后 AUC 0.8884 与测试集 0.8827 接近，说明没有明显过拟合。真正的验证要靠 A/B 实验，这是下一步。

**Q10：为什么阈值不用 0.5？**
A：正样本只有 15.5%，0.5 会过度保守导致召回塌陷。用 PR 曲线取 F1 最优得到 0.59，兼顾精确率与召回率。这个细节最能体现对不平衡分类的理解。

**Q11：这个项目能落地到真实企业吗？**
A：可以直接替换数据源跑通，需要的改造是：① 对接 CRM 数据仓库；② 接真实触达通道（短信/企微/邮件 SDK）；③ 加权限与审计；④ 建立 ROI 回流闭环做持续优化。

**Q12：为什么前后端分离？怎么部署的？**
A：前端可独立部署与独立回滚；后端只提供 JSON API，方便以后接 App、小程序、第三方系统。部署**只有一种前端方式——Nginx**：静态资源由 Nginx 托管、`/api/` 反代到 FastAPI，同源访问不需要 CORS。同一套配置有两种跑法：① 本机 `.venv` + 本地 Nginx（`deploy/nginx.conf`，改代码方便）；② Docker Compose（`docker compose up -d --build`），web 容器就是 Nginx、api 容器是 FastAPI，只有 web 对外暴露 8080，后端在容器内网。**换机器交付时用 `deploy/make-bundle.ps1` 打离线包**（镜像 + compose + 说明），目标机 `docker load` 后 `up -d`，不用装 Python/Node、不用联网——这一条最能打动"评委问你怎么交付"。

**Q13：项目里有没有用到大模型？**
A：有，但是**可选的**：配了 `LLM_BASE_URL/LLM_API_KEY` 就走 Function Calling，不配就走规则引擎。既展示大模型应用能力，又保证离线可演示——这是工程上很实用的取舍。

**Q14：为什么写这么多个后端模块，不能一个文件？**
A：一个文件写到 1500 行无法维护也无法测试。这里按「指标/分层/聚类/画像/预测/关联/结论/方案」单一职责拆分，每个模块都能单独跑、单独验证，`store` 负责组装与缓存。

## 9. 主动承认的不足（比藏着更有说服力）

1. 数据规模小、单时点快照，没有时间序列趋势与因果推断
2. 关联规则提升度接近 1，实际推荐价值有限（结论里已转成"组合套餐"建议）
3. 响应模型是线性模型，特征交互靠人工构造
4. 没有 A/B 实验与 ROI 回流闭环，ROI 是估算不是实测（理想口径，未含物流/退货/毛利）
5. 前端未做权限与多租户，生产部署还需要 Nginx + 鉴权

## 10. 下一步计划（被问"还能做什么"时用）

1. 接入真实触达通道 + A/B 实验框架，把 ROI 从估算变成实测
2. 用 GBDT（LightGBM/XGBoost）+ 特征交叉对比线性模型，目标 AUC 0.90+
3. 加入客户生命周期价值（CLV）预测与时间序列流失预警
4. 把分析结果物化到数据库，支持千万级数据与多租户
5. Agent 增加「多轮追问 + 报告一键导出 + 大模型自动生成结论文案」
